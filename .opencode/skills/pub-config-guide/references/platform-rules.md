## 环境语义

- 每个配置包维护三套独立环境数据：`sit`、`prod_test`、`prod`。
- 本地开发环境和其它常见内网联调环境通常读取 `sit`。
- 预发页面读取 `prod_test`。
- 线上页面读取 `prod`。
- `prod` 不能直接编辑，只能从 `prod_test` 流转。

使用这些语义做判断：

- 用户说“本地联调不生效”，优先检查 `sit`。
- 用户说“预发页面不对”，优先检查 `prod_test`。
- 用户说“线上发布”，不要直接改 `prod`，而是走 `prod_test -> prod`。

## 权限规则

应用配置包：

- 查看配置包、配置项和配置数据：所有人
- 新建配置包：`owner`、`developer`
- 修改配置包信息：`owner`、`developer`
- 创建、删除、修改配置项：`owner`、`developer`
- 修改配置数据：`owner`、`developer`、`tester`
- 删除配置包：`owner`

公共配置包：

- 所有操作默认由创建人操作

附加权限：

- `prod_test -> prod` 的流转，只有 `owner` 和具备对应附加权限的用户才能操作

如果权限不够：

- 直接告诉用户缺的是哪类权限
- 不要继续猜测执行结果
- 不要把“可能能发”描述成可执行结论

## 发布约束

- 环境流转只能按顺序推进，不能跨环境。
- `sit -> prod_test`
- `prod_test -> prod`
- 发布到 `prod` 时，`issueKey` 必填。
- `issueKey` 优先从当前 Git 分支提取；能稳定提取时直接使用。
- 发布到 `prod` 前，应先确认 `prod_test` 已验证。

回滚规则：

- 优先通过平台历史记录选择版本回滚。
- 执行前先看 diff，再决定是否回滚。
- 不要把应用资源流转能力错用到配置包数据流转上。

## 排查时的判断要点

看到“配置改了但没生效”时，优先区分是哪一类问题：

- 环境判断错误：用户改的是 `sit`，但访问的是预发或线上
- 权限约束：没有权限完成流转，导致目标环境数据未更新
- 发布链路错误：误以为 `prod` 可直接编辑，或误用其它发布 tool
- 页面接入错误：应用未注入配置包，或代码仍在读旧字段

建议先把问题归类，再决定去看平台状态还是本地代码。
