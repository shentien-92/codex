# 代码复用思考指南

> 用于在动手前发现重复模式，避免把同一概念散落到多个地方。

---

## 何时打开

- 你正在写的代码和现有代码很像
- 同一种模式出现 3 次以上
- 正在修改常量、配置、字段名、事件名、命令名
- 正在创建新的 utility/helper function
- 正在把同一份数据传给多个消费者

---

## 修改前搜索

先搜索概念本身，而不是只搜索文件名。

```bash
rg "concept_or_value"
rg "existingFunctionName"
rg "field_name"
```

搜索目标包括：

- 同名或近似命名的 helper
- 同一常量值
- 同一字段在 API、类型、测试、文档中的出现
- 相同错误信息或用户可见文案

---

## 判断是否应该复用

优先复用已有 abstraction，当它已经表达了同一业务概念或技术边界。

不要为了少两行代码强行抽象。只有当抽象能减少真实复杂度、避免一致性风险，或符合现有
模块边界时才新增。

---

## 新增 helper 前的检查

- [ ] 是否已有同职责 helper？
- [ ] 是否只有一个调用点？如果只有一个，通常先内联。
- [ ] helper 名称是否表达领域概念，而不是实现细节？
- [ ] 是否会把不相关模块耦合在一起？
- [ ] 测试是否覆盖 helper 的主要边界？

---

## 常见风险

- 改了常量值，但测试 fixture、schema、snapshot 或文档没有同步。
- 新增了 helper，却只被调用一次。
- 抽象跨越了不该跨越的层，让依赖方向变差。
- 复制现有模式时漏掉 error handling 或 cleanup 分支。

---

## 输出要求

如果你决定复用或不复用，都应能说清楚：

- 复用点是什么；
- 为什么它和当前需求是同一概念；
- 如果不复用，差异在哪里；
- 后续新增同类需求时应走哪条路径。
